Memory Subsystem · Testing Playbook

How to verify the memory architecture works.

You can prove all 23 invariants of the memory layer without Neo4j, without Ollama, and without ingested documents. Then once those are live, run the full multi-turn chat tests in the UI.

1. The fast path — two double-clicks

No Neo4j needed. No Ollama needed. Just PostgreSQL (which you already have from RUN.bat).

① Double-click TEST.bat

Runs test_memory.py against your live PostgreSQL. Verifies all 23 memory invariants in about 5 seconds. Window stays open at the end.

What it tests: promoter regex, PII gate, explicit-wins rule, top-k filter, recent-messages order, assembler order & budgets, citation roundtrip, cascade delete, watermark persistence.

② Double-click INSPECT.bat

Read-only viewer that dumps the contents of every memory table: users, chats, messages, message_citations, chat_memory, user_memory.

Use to: see what's actually been written after a manual chat session in the UI.

3. What each of the 23 checks proves

0

Sanity

Connects to the live database, finds the seeded omar user. If this fails, your DB isn't initialized — run RUN.bat once first.
1

Promoter regex allowlist (6 patterns)

Each of the six promotion patterns recognises its trigger phrase and creates the right row in user_memory with the right category, memoryKey, source='inferred' and confidence=0.7.
2

PII gate

When a user message contains a sequence of 10+ digits (account number, NID), the promoter refuses to extract anything from it. Also unit-tests containsPii() directly.
3

Explicit always wins

If language=Arabic is set explicitly via the settings page (source='explicit'), the promoter cannot overwrite it from a chat phrase like "always answer in English". This protects user intent.
4

Prompt-injection filter

When loading user memory for the prompt, only preference + instruction rows are returned. profile and domain stay out of the prompt (used for retrieval bias).
5

Recent-messages order

Returns the last N messages in oldest-first order so the model sees a natural chronological window. Tested with 8 messages, asks for the last 4.
6

Assembler structure (7 sub-checks)

The final prompt has all six blocks in canonical order: system → user mem → chat summary → recent turns → context → reminder → question. Each block is present and content is in the right slot.
7

Citations roundtrip

Inserting 2 citations for a message persists them with correct ranks (1, 2) and they're retrievable by message id.
8

Cascade delete

Deleting a message removes its citations automatically (FK ON DELETE CASCADE). No orphan rows in the audit trail.
9

Watermark persistence

The new lastSummarizedMessageId and summaryTokens columns on chat_memory save and load correctly — proves the summarizer can be incremental.
10

Cleanup

All test rows for omar are deleted at the end so the test is idempotent. Re-running it doesn't accumulate junk.
23

Total assertions

11 sections, 23 individual checks. Sections 1 and 6 each contain multiple sub-checks.

4. Using INSPECT.bat after a chat

After you've used the chat in the UI, run INSPECT.bat to see what was actually stored. Here's what you should expect to see, table by table:

messages — every turn of every chat

One row per user message + one row per assistant answer. Should show both roles. Look at createdAt to verify per-turn timing.

message_citations — provenance, NEW table

For every assistant message, one row per retrieved chunk with its chunkId, docName, similarity score, and rank. This is your full audit trail of "which answer cited which chunk".

chat_memory — per-chat rolling summary

One row per chat. Stays empty until the summarizer fires (≥6 new turns or ≥1000 new tokens). After that, summary contains the LLM-written recap, summaryTokens shows its size, and lastSummarizedMessageId marks the watermark.

user_memory — long-term preferences

Rows only appear when:

  • You explicitly hit the PUT /api/memory/user/{key} endpoint (settings page, future UI) → source='explicit', confidence=1.0.
  • You say a trigger phrase like "always answer in Arabic" in a chat and the promoter fires → source='inferred', confidence=0.7, evidenceChatId points to that chat.

5. Manual chat-UI tests (after Neo4j + Ollama are live)

These are the user-visible behaviors. Run them once a real chat answer can be generated. They prove the memory layer is wired correctly all the way to the model.

A

Multi-turn reference resolution

  1. Log in as omar.
  2. Start a new chat. Ask: "ما هي متطلبات الترخيص في الفصل الأول؟"
  3. After the answer streams, ask: "وماذا عن الفقرة الثانية؟"
  4. Expected: the model resolves "الفقرة الثانية" against the licensing topic, not as a brand-new question.

How to verify: the prompt logged in the FastAPI window should show "RECENT TURNS" with your prior Q/A; if it's missing, the wiring is broken.

B

User preference promotion across chats

  1. In chat 1, ask: "always answer in Arabic". Wait for the assistant reply.
  2. Run INSPECT.bat → user_memory should have a row: language='Arabic', source='inferred', evidenceChatId={chat1.id}.
  3. Click + New chat. Ask any question in English.
  4. Expected: the model answers in Arabic, because the preference was injected at the top of the prompt.
C

Citation persistence

  1. Ask any question that produces citations [chunkId] in the streamed answer.
  2. Run INSPECT.bat → the message_citations table should list one row per cited chunk, with the same chunkId values, plus a rank and score.
D

Summarizer debounce

  1. In one chat, ask 5 quick questions. After each, run INSPECT.bat on chat_memory.
  2. Expected after <6 turns: summary is empty, lastSummarizedMessageId is null. (The debounce hasn't fired.)
  3. Ask a 6th, then a 7th question.
  4. Expected: after the 6th or 7th, summary populates with an LLM-written recap, lastSummarizedMessageId points at the latest message, summaryTokens > 0.
E

Explicit-wins guarantee

  1. Manually insert an explicit preference: PUT /api/memory/user/language with { "memoryValue": "Arabic" } using curl or Postman.
  2. In a chat, say "always answer in English".
  3. Run INSPECT.bat → user_memory.language is still Arabic with source='explicit'. The promoter saw the explicit row and refused to touch it.
F

Right-to-be-forgotten / cascade

  1. Note a chat id and its messages from INSPECT.bat.
  2. Delete the chat via the UI (or DELETE /api/chats/{id}).
  3. Expected:
    • messages, message_citations, chat_memory for that chat are gone (FK CASCADE).
    • Any user_memory row whose evidenceChatId pointed at it still exists, but the field is now NULL (FK SET NULL). The preference survives; its provenance is severed.

6. If something doesn't pass

SymptomMost likely causeFix
Test 0 fails — no omar user DB isn't initialized Run RUN.bat once. It applies migrations + seeds.
Test 5 fails — recent-messages order Messages share a timestamp (rare in real use; only in artificial tests) Test now commits between inserts to mimic real per-turn behavior. Should pass.
Manual test A fails — no multi-turn behavior Server was started before the migration; old code path still cached Stop the server window (Ctrl+C), then RUN.bat again.
Manual test B fails — preference not applied in new chat Promoter ran but injection at prompt time isn't wired Check the FastAPI window for userMem=… in the streaming log. If it shows userMem=0, no preferences were loaded.
Manual test D — summary stays empty after 10+ turns Summarizer can't reach Ollama, or chat model isn't pulled Check Ollama is running on :11434 and ollama list includes a chat model. The summarizer always uses the local Ollama, not Groq.
INSPECT.bat can't find psql PostgreSQL bin not on PATH Edit INSPECT.bat and set PSQL to your psql.exe path manually.
Bottom line. If TEST.bat shows ALL 23 CHECKS PASSED, the memory plumbing is fully verified. Once Neo4j + Ollama + ingested data are live, manual tests A-F prove the user-visible behaviors. Until then, the database-side tests give you all the confidence you need to ship this part of the system.
